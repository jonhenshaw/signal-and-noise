Running LLMs Locally That Don't Suck

Apr 15, 2026 · 10 min read · LLMsSelf-HostingPerformance

The State of Local LLMs

Two years ago, running a local LLM meant accepting terrible quality. Today, a 7B parameter model quantized to 4-bit can hold its own against early GPT-4 on many tasks. The gap has narrowed dramatically.

Hardware Requirements

Here's the reality of what you need:

Model SizeVRAM (4-bit)VRAM (8-bit)
7B6 GB12 GB
13B10 GB20 GB
30B20 GB40 GB
70B40 GB80 GB

If you have a Mac with Apple Silicon, unified memory means you can run much larger models than the dedicated VRAM numbers suggest. A Mac Studio with 64GB can comfortably handle 30B models.

Tools That Actually Work

llama.cpp / Ollama

The gold standard for CPU/GPU inference. GGUF format, efficient quantization, and it runs on literally everything. Ollama wraps it in a nice API.

# Install Ollama, pull a model, run it
brew install ollama
ollama pull qwen2.5:7b
ollama run qwen2.5:7b "Explain quantum computing"

LM Studio

GUI-first approach. Great if you want to browse models, compare outputs, and not touch the terminal. The model browser alone is worth the install.

vLLM

If you need an OpenAI-compatible API server with high throughput, this is the tool. Continous batching, PagedAttention, and proper concurrency support.

Quantization: The Real Deal

4-bit quantization (Q4_K_M) loses maybe 5-10% quality but cuts memory requirements by half. For most tasks, the trade is worth it. Go to 8-bit if you need the extra quality and have the memory.

Pitfalls to Avoid

  • Don't run unquantized models unless you have enterprise GPUs
  • Don't ignore context window costs — 128K context eats RAM fast
  • Don't skip benchmarking — model quality varies wildly by task
  • Don't assume bigger is better — a well-optimized 7B beats a poorly-run 70B

The best local LLM setup is the one that's fast enough that you actually use it.
